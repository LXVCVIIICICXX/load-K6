# load-test — нагрузка на сайт и разбор того, что получилось

Инструмент для нагрузочного тестирования веб-платформы: Playwright записывает
живую сессию из браузера, кодоген превращает её в k6-сценарий, k6 его гоняет,
Python собирает по нему самодостаточный HTML-отчёт, а локальная веб-морда всем
этим управляет.

Готовых сценариев в поставке нет: любой такой ходил бы по путям чужого сайта.
Сценарий берётся из записи вашего — с ваших адресов, с вашим порядком запросов.

Ни одного адреса, пароля или id стенда в коде нет — всё приходит из `.env`
и локальных конфигов, которые в репозиторий не попадают.

```
  запись браузером  →  har/*.har  →  codegen.py  →  recorded/*.js
  recorded/*.js     →  run.py     →  results/<стенд>/<прогон>/report.html
```

---

## Что нужно

| | зачем | без него |
|---|---|---|
| **k6** | генератор нагрузки | ничего не запустится |
| **Python 3.8+** | запуск, отчёты, морда | ничего не запустится |
| **Node 18+** | запись сценариев браузером (Playwright) | запускать нечего: сценарии берутся только из записей |

Сторонних Python-пакетов нет: только стандартная библиотека.

## Разворачивание

```bash
git clone <адрес репозитория>
cd load-test
./setup.sh
```

`setup.sh` проверит инструменты, доставит недостающее (k6 — через brew, для
Debian/Ubuntu покажет команды с sudo), поставит Playwright с браузером,
создаст `.env` и локальные конфиги из примеров и сгенерирует файлы, которые
сценарии загружают на стенд.

Playwright живёт в `recorder/node_modules`, и это единственная зависимость,
которую надо ставить. Пока её нет, запись не стартует, а морда отвечает
«рекордер не установлен: выполните ./setup.sh (или npm install в recorder/)».
Руками, если `setup.sh` пропустили или он споткнулся на npm:

```bash
cd recorder && npm install && npx playwright install chromium
```

Дальше — файлы под свой сайт; обязателен из них только `.env`. Ничего из
этого в репозиторий не попадает.

**1. `.env`** — адрес, вход и профили (полный список полей с пояснениями лежит
в `.env.example`):

```ini
API_URL=https://api.stage.example.com
SITE_URL=https://stage.example.com

# как устроен вход именно на этом сайте
CSRF_PATH=/sanctum/csrf-cookie      # если токен выдаётся отдельным запросом
LOGIN_PATH=/api/v1/login
LOGIN_BODY={"email":"$USER","password":"$PASS"}
LOGIN_CONFIRM_PATH=                 # второй шаг, если вход двухступенчатый
LOGOUT_PATH=

USER_EMAIL=user@example.com         # профиль роли «user»
USER_PASS=…
ADMIN_EMAIL=…                       # профиль роли «admin»
ADMIN_PASS=…
ROLE=user                           # кем ходит сценарий, ходящий одной ролью
SITE_AUTH=                          # «логин:пароль», если фронт закрыт basic-авторизацией
```

**Про роли.** Роль — метка, которую придумываете вы: `user`, `reviewer`,
`admin`, `buyer`. Списка ролей у инструмента нет и быть не должно — он не знает,
как устроены права на вашем сайте. Из метки складывается имя переменных:
`user` → `USER_EMAIL`/`USER_PASS`, их же берёт `creds('user')` в сценарии.
Теми же метками помечены профили в `users.json` и запросы в `requests.json`.

Инструмент не знает вход конкретного сайта и не должен: подсмотреть путь и
тело проще всего в записи браузера («Отчёты» → «Записи браузера») или в
спецификации API.
В телах доступны три подстановки: `$USER`, `$PASS` и `$resp.<путь через точку>`
в ответ первого шага — так описывается двухступенчатый вход:

```ini
LOGIN_CONFIRM_PATH=/api/v1/confirm-login
LOGIN_CONFIRM_BODY={"id":"$resp.data.options.0.id","token":"$resp.data.token"}
```

> Профили должны существовать на сайте заранее — сценарии никого не заводят.
> Проверь вход руками: на многих сайтах несколько неудачных попыток блокируют
> учётку на десятки минут, и дальше тест меряет блокировку, а не сервер.

**2. `requests.json`** — необязательный. Карта запросов сайта: имя, путь и чьей
сессией ходить. Прогоны по ней больше не идут — сценарий целиком приходит из
записи, — но её читает сверка покрытия спецификации API. Скопирован из
`requests.example.json`:

```jsonc
{
  "requests": [
    {"name": "login",     "role": "S", "login": true,       "weight": 12},
    {"name": "items",     "path": "/api/v1/items?limit=20", "role": "S", "weight": 30},
    {"name": "item.show", "path": "/api/v1/items/{ITEM_ID}","role": "S", "weight": 20},
    {"name": "report",    "path": "/api/v1/admin/report",   "role": "T", "weight": 1}
  ]
}
```

`role` — чьей сессией ходить: та самая метка из `users.json`. Поля `weight` и
`login` остались от прежних рукописных сценариев и сейчас ни на что не влияют.
Откуда брать пути: из спецификации API или из записи браузера — смотрите, что
реально шлёт фронт.

`pool.json` (подстановки вида `{ITEM_ID}` в путях) — оттуда же: подставлять их
было некому с тех пор, как сценарии стали приходить из записей, где адреса уже
настоящие. Файл читается и раздаётся в прогон, но пустой никому не мешает.

Готово:

```bash
./start.sh          # морда на http://127.0.0.1:5057
```

Порт задаётся переменной `WEB_PORT` — в `.env` или разово при запуске:
`WEB_PORT=4044 ./start.sh`.

Дальше — вкладка «Отчёты» → «Записи браузера»: без записи запускать нечего.

## Морда

`./start.sh` поднимает локальный интерфейс (только 127.0.0.1 — он знает
секреты и запускает процессы). В нём:

* **Запуск** — выбор сценария, паттерна нагрузки и длительности, живой лог и
  прогресс; под каждым сценарием расписано, какие запросы он шлёт и в каком
  порядке. Пока записей нет, выбирать нечего и список пуст.
* **Отчёты** — две вкладки: «Прогоны нагрузки» (каждый открывается своим
  HTML-файлом) и «Записи браузера» — там же и снимается новая запись: жмёте
  «Записать», проходите сценарий руками, на выходе HAR и собранный из него
  k6-скрипт.
* **Пользователи** — включение и отключение учёток, вес в пуле; лежат в
  `users.json`, оттуда же раздаются в сценарии.
* **Настройки** — Beszel, Telescope и фронт стенда (адрес и basic-авторизация
  для записи); пишутся в `secrets.json` с правами `0600` и наружу никогда не
  отдаются. Там же — спецификация API.

## Спецификация API

Файл Swagger или OpenAPI стенда кладётся перетаскиванием в «Настройки» →
«Спецификация API» и ложится в каталог `api/`. Нужен он для одного: сверить,
что из заявленного API ваши записи вообще трогают.

Спецификаций может лежать несколько — запросы из них складываются. Формат:
`.json` всегда, `.yaml` — только если в системе есть PyYAML (своих
зависимостей у инструмента нет; Swagger UI отдаёт ту же спецификацию в JSON).
Файл разбирается до записи: непохожий на спецификацию на диск не попадёт.

Каталог `api/` закрыт в `.gitignore`: спецификация — это карта чужого стенда,
а репозиторий публичный.

Кнопка **«Подробно»** у файла раскрывает саму доку — операции разделами, с
поиском и с отметкой покрытия справа: галочка значит, что операцию шлёт хотя бы
один сценарий, наведение показывает какой. Разделы свёрнуты (поиск раскрывает
найденное сам), а строка операции раскрывается в подробности: описание,
`operationId`, параметры, тело с полями и ответы — то же, что показывает дока,
со снятыми `$ref`.

Покрытие считается по коду сценариев, а не по прогонам, — вопрос здесь «что мы
вообще умеем нагружать». Пути берутся из карт `recorded/*.flow.json`, которые
кодоген кладёт рядом со сценарием, и из `requests.json`, если он заполнен.

Чего покрытие НЕ говорит:

* **не про долю нагрузки** — запрос раз за сессию и запрос на каждой итерации
  оба отмечены галочкой;
* **пишущие операции** почти все и останутся непокрытыми: запись браузером
  снимают на чтении, чтобы прогон не наплодил данных на стенде. Поэтому в
  сводке две цифры — по всем операциям и отдельно по `GET`;
* **`OPTIONS`** в сверку не идут: preflight — разговор браузера с nginx, а не
  операция продукта.

## Сценарии

**Ни один сценарий в репозиторий не попадает** — см. `.gitignore`. Сценарий это
карта конкретного сайта, даже когда адреса в нём приходят из конфига, поэтому
после `git clone` их нет вовсе: первый берётся из вашей записи браузера.

Морда не держит список тестов в коде — она смотрит на диск. Тестом считается
любой `*.js` рядом с кодом и в `recorded/`, кроме помощников `_lib.js`,
`env.js`, `errlog.js`. Имя и описание берутся из шапки самого файла, а какие
поля показать в форме запуска — из того, какие переменные сценарий читает:
`TARGET` даёт поле «какой запрос разгоняем», `ROUNDS` — «сколько проходов»,
`STAGES` — профиль нагрузки. Положили файл — он появился в списке.

Запуск:

```bash
python3 run.py <сценарий>.js [--name ИМЯ] [ПЕРЕМЕННАЯ=ЗНАЧЕНИЕ …]
python3 run.py recorded/<сценарий>.js --name ИМЯ
```

Полезные переменные: `STAGES` (ступени нагрузки в формате k6), `VUS`,
`GRACEFUL`, `ROLE` (чьей учёткой ходить), `ACCOUNTS`, `SMOKE=1` (один проход
без пауз — проверить, что сценарий проходится целиком), `THINK=0` (убрать
паузы), `STATIC=0` (не грузить статику фронта).

Результат — `results/<стенд>/<имя>-<дата>/report.html`: графики темпа и
задержек, разбивка по запросам, тела ошибок и, если настроен Beszel, — CPU,
сеть и контейнеры сервера в те же секунды.

## Запись сценария

Кнопками — во вкладке «Отчёты» → «Записи браузера». То же самое руками:

```bash
# 1. записать: откроется браузер, пройдите сценарий руками и закройте окно
node recorder/record.mjs --out har/moya-zapis.har --url "$SITE_URL"

# 2. собрать k6-скрипт из записи
python3 codegen.py har/moya-zapis.har --out recorded/moya.js --name "Моя запись"

# 3. смоук — проверить, что сценарий проходится целиком
python3 run.py recorded/moya.js --name смоук SMOKE=1 STAGES='[{"target":1,"duration":"1s"}]'
```

Кодоген вырезает из записи вход вместе с паролем и подставляет общий вход из
`_lib.js` (тот, что описан в `.env`),
паузы берёт из настоящих интервалов между запросами, а параллельные пачки
оставляет пачками — браузер шлёт их одновременно, и по нагрузке это не то же
самое, что те же запросы по очереди.

## Разбор записи

```bash
python3 har.py har/moya-zapis.har                    # слои: кэш, статика, бэкенд
python3 har_report.py har/moya-zapis.har             # HTML-отчёт по записи
python3 telescope.py --har har/moya-zapis.har --out tele.json   # что видел Laravel Telescope
python3 har_report.py har/moya-zapis.har tele.json   # запись и бэкенд рядом
python3 analyze.py --last                            # деградация по последнему прогону
python3 cleanup.py                                   # показать мусор в results/ (--apply удалит)
```

## Что где лежит

```
run.py           запуск k6 + сборка отчёта        web.py / web_ui.html   морда
config.py        .env, пути, вход, имя стенда     aggregate.py           разбор потока k6
env.js           адреса и профили для сценариев   report_html.py, charts.py  отчёт прогона
_lib.js          хелперы сценариев, вход          har.py, har_report.py  разбор записи
errlog.js        тела неуспешных ответов в отчёт  codegen.py             HAR → k6-сценарий
recorder/        запись браузером (Playwright)    telescope.py           выгрузка из Telescope
mocks/           файлы для загрузки (генерируются) analyze.py, cleanup.py прочее
api/             спецификации Swagger/OpenAPI     apispec.py             их разбор
coverage.py      сверка сценариев со спецификацией
har/             записи браузера        recorded/  сценарии из записей     results/  прогоны
```

Локальные файлы под свой сайт (в репозиторий не попадают): `.env`,
`requests.json` (карта запросов для сверки покрытия), `pool.json`,
`users.json` и `accounts.json` (профили), `secrets.json` (Beszel и Telescope),
`phases.json` (необязательно: разделы сайта для разбора записи).

По умолчанию `har/` и `results/` лежат рядом с кодом. Если записи и прогоны уже
накоплены в другом каталоге — укажите его в `LOAD_ROOT`.

## Секреты

Данные площадки в репозиторий не попадают — что именно исключено, перечислено
в `.gitignore`; парные `*.example.json` показывают формат. В коде нет ни одного
адреса, пароля, пути и id: всё приходит из `.env` и локальных конфигов, поэтому
инструмент одинаково годится для любого сайта.
